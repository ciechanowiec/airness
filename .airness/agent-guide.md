# Airness Agent Guide

This guide maps the governing standard, `README-guideline-software-project.adoc`, to the Airness harness for every repository, whatever stacks it holds. The guide of each stack layer present adds to it, and the managed blocks of `AGENTS.md` name them. After them, follow the remaining steps of `AGENTS.md` in the order it declares. Exact analyzer rules remain in the executable harness.

## Harness Invariants

- Each module inherits the Airness parent for what it contains: `airness-parent` for a monorepo root or a module with no code, `airness-parent-java` for Java, `airness-parent-spring-boot` for a Spring Boot project, or `airness-parent-node` for a module whose main content is JavaScript or TypeScript. That choice is the only place a module states which kind it is, and it is what decides which rules apply.
- Use exactly Java 25, Maven 3.10.0 or later, and a Git working tree. Default verification reads Maven Central, Docker Hub and GitHub and fails when any of them cannot be read, and Extended verification also needs a reachable Docker daemon that can read the repository through a bind mount. Extended verification refuses to start under `-o` or offline mode, because Maven skips a goal whose descriptor requires online mode, the vulnerability scan is one of those, and an offline run would otherwise report clean without having read a single advisory. Default verification also needs online Maven mode from `prepare-package` onward, because Maven otherwise skips SBOM generation, including with `-DskipTests`; earlier phases keep their offline behavior. On macOS with Colima, a repository under Downloads, Desktop or Documents is unreadable inside a container until the terminal that starts Colima is granted access to that folder under System Settings, Privacy and Security, Files and Folders, so keep the repository elsewhere or grant it.
- Treat every finding and every tool, setup, or compilation failure as a failed verification. Reporting findings with `-Dairness.enforce=false` is not a pass. A build using `-DskipTests` produces no Airness verdict.

## Governed Domains

Airness governs all of the following domains:

- **Toolchain and Maven model:** runtime versions, project and parent coordinates, package ownership, inherited plugin ownership, raw-model anti-bypass checks, effective dependency convergence, the ordering and local use of declared properties, valid Airness parameters, and current build practices: no Java version below 25 stated in the project file, no superseded coordinate, a version on every managed dependency, a groupId on every plugin, `project.`-prefixed expressions, the documented order of pom elements, and Java 21 or later in every workflow's `setup-java`. Every pom is laid out one way: exactly one blank line sets each element written directly inside `<project>` that holds elements, such as `<parent>`, `<licenses>` or `<build>`, apart from its neighbours, and stands above the comments written directly over it; no two blank lines follow each other; no blank line stands directly after an opening tag or directly before a closing one; and every tag starts its own line, apart from the closing tag of an element that holds only text, so `<name>MIT</name>` stays on one line and `<license><name>MIT</name></license>` does not. Maven hands a child its parent's metadata, and the chain above a project ends in Airness, so the repository's root pom declares the project's own `<name>`, `<description>`, `<url>`, `<inceptionYear>`, `<licenses>`, `<developers>` and `<scm>` with its `<url>`, `<connection>` and `<developerConnection>`; `<organization>` is optional. Each license is named by an identifier the SPDX license list does not mark deprecated, spelt as the list spells it, or by `LicenseRef-Proprietary` for code no public license covers, whose terms come from a contract; never by `Unlicense`, which gives the code to the public domain, or by another `LicenseRef-`. The `<url>` and the `<scm>` `<url>` are one `https://` address, and both connections start with `scm:git:`. The `<inceptionYear>` is four digits and follows neither the current year nor the repository's first commit. The name and the description hold no `@PLACEHOLDER@`, the description does not repeat the name, and no value repeats one an Airness pom declares. A module below the root inherits no metadata field from an Airness pom, so a module that inherits an Airness parent directly declares its own. Every module writes `<modelVersion>4.0.0</modelVersion>`; its group is a reverse domain of at least two lower-case segments that is not, and lies under none of, `com.example`, `org.example` and `net.example`; its artifact is lower-case words joined by hyphens and, below the root, its directory's name; and its version is `major.minor.patch`, optionally `-SNAPSHOT`, each judged by the value it resolves to. No pom, profiles included, activates a profile by default, by operating system, by JDK or by an `env.` property, declares `<reporting>`, declares `<prerequisites>` unless its packaging is `maven-plugin`, writes a `<distributionManagement>` `<status>` or `<relocation>`, moves a source or output directory directly under a `<build>`, or names a module or a parent `<relativePath>` outside the repository. The dependency license allowlist passes over artifacts of the project's own group, which carry the license its root pom states. Every hosted Ubuntu runner a workflow, a composite action or an Azure Pipelines definition names runs the current Ubuntu long-term-support release, named rather than aliased: `ubuntu-26.04`, or `ubuntu-26.04-arm` for Arm. `ubuntu-latest` and every earlier release are refused wherever the label is written, a matrix value included, and a larger runner whose label carries a release is held to it too. The required release moves to the next long-term-support one only once GitHub-hosted runners for it are generally available. Every action a workflow or a composite action uses declares `node24` or later in the `runs.using` key of the `action.yml` or `action.yaml` at the ref it is pinned to, or runs as a `docker` or `composite` action; a composite action's own actions are held to the same rule, and a refusal found there names the action that declares the old runtime. The runtime is read from GitHub, never from the version comment beside a pinned commit, and the metadata of a commit is kept under the local Maven repository, so it is read once; a tag or a branch is read again on every build. A `GITHUB_TOKEN` in the environment is sent to GitHub over HTTPS alone, for an action in a private repository or under a rate limit, and printed nowhere. A local action is judged where it lives, by the runtime its own `action.yml` under `.github/actions` declares; a `docker://` image and a reusable workflow are not actions and are passed. A `uses:` value holding an expression, outside the form `owner/repo[/path]@ref`, or naming a ref that holds no metadata, and metadata declaring no runtime GitHub runs actions on, are refused rather than passed, and GitHub failing to answer fails the build rather than reporting the action. Repair a finding by pinning a release of the action whose metadata declares the required runtime. The required runtime moves to the next one only once GitHub has deprecated `node24` for actions, never merely because a later Node exists. Every module ends with `airness:module-complete`, the last execution of `verify`: a project binds nothing in `verify` and names no goal after it, and either is refused at `validate`. Bind a project step to an earlier phase, such as `post-integration-test`, and name a command-line goal before the lifecycle (`mvn sonar:sonar verify`) or run it in an invocation of its own. Once every module of the build has completed, one closing step compares the committable tree with the one the build started from, holds the Java sources and the node projects' own code to their suppression ceilings, refuses every module of the build that holds code (Java under its source roots, or a `package.json`) without inheriting an Airness parent, and under Extended verification writes the compliance report and looks up in the OSV database every npm package and every package of each image the `image` gate builds. Build Helper and Assembly are optional managed plugins: declare one without a version in the module that uses it. Build Helper's source and resource roots and Assembly's distribution descriptors belong to the project.
- **Repository files and instructions:** managed, seeded, and forbidden files; no license file beside the root pom, whose `<licenses>` states the project's license; agent instruction files; editor and Git configuration; and an unchanged committable tree during verification. Managed files follow what the repository contains rather than which parent a module names: the root carries the files of every stack present in any module, `AGENTS.md`, `.gitignore` and `.dockerignore` lead with one marked block per stack, the lines below the blocks belong to the project, and each declared node project carries the node files in its own directory. No ignore file repeats a pattern an earlier declaration already applies: a line equal to an earlier line of its own file, or an un-anchored `.gitignore` line (no slash but a trailing one) equal to a line of a `.gitignore` in a directory above, with no line of the other polarity between them that could reverse it. In a `.gitignore` only a line that may match a path the pattern matches can, so a `!.vscode/settings.json` between two `*.iml` lines keeps neither; in a Docker ignore file any line of the other polarity does. A managed line counts as declared, so remove the project's copy; a Docker ignore file is compared with itself alone. No `.gitignore` negation sits beneath a directory an exclusion hides, because git never looks inside an excluded directory: exclude the directory's contents (`.vscode/*`) rather than the directory when a file in it is to be kept. The editor configuration is held against the files a commit would carry, so what git is configured to ignore is passed over rather than reported: build output and a tool's scratch are not content this style governs. Neither is a generated file, which is a file a stack layer, `airness.generated.files` or a node project's `airness.generatedArtefacts` declares, and which the editor configuration, the indentation check and the typography check leave unread. The indentation check holds the rest to the editor configuration too: it reports the first line of each file whose leading whitespace is not the kind `indent_style` names, and in a YAML file the first nesting step that is not `indent_size` columns wide, and passes over the binaries and tab-separated data the file linter exempts. Ignored files selected as Java or resource inputs are different: Maven can consume them locally while a checkout omits them. The per-module `build-inputs` preflight rejects that mismatch at `validate`, `process-resources` and `process-test-resources`, using Maven's roots and file filters, and so it does for a script or stylesheet under a checked source root of a declared node project. Track an intended repository input, including a vendored distribution file hidden by an ignore pattern, or generate it beneath a reactor project's configured Maven build directory. Generated inputs there and ordinary non-ignored new files remain valid. No project allowlist is provided, and report-only mode does not excuse a preflight failure. Arbitrary custom-tool file reads are outside this check, so it does not establish general provenance for everything a build can read.
- **Repository content:** every image of a supported format (PNG, JPEG, GIF, WebP, ICO) decodes; every file path an `AGENTS.md` names in backticks exists beside it or at the root, unless it is a module specifier of a dependency the `package.json` there declares; every npm script it names, backticked or after `pnpm run`, is declared by that `package.json`; every `.claude/skills/**/SKILL.md` opens with frontmatter whose kebab-case `name` equals its directory, whose `description` says when to use it, and whose keys are all ones the agent runtime knows; every variable a compose file interpolates without a default is documented in `.env.example` (or `.env.sample`, `.env.template`) and supplied by every workflow that runs Maven through `verify`; every such example file, wherever it lies, leaves each variable whose name holds `PASSWORD`, `PASSWD`, `SECRET` or `TOKEN`, or ends in `KEY`, empty (`NAME=`), so no copy of it supplies a default credential; no compose service publishes on a host port the file fixes, a literal or a variable's default, or names its container, so two checkouts or two projects start side by side; no compose service runs `privileged`, adds a capability with `cap_add`, sets a `security_opt` that is `unconfined` or `label:disable`, shares a namespace of the host (`network_mode`, `pid`, `ipc`, `userns_mode`, `uts` or `cgroup` set to `host`) or mounts the Docker socket; every port a compose service publishes binds the loopback interface, as in `127.0.0.1:${APP_PORT}:8080` or `host_ip: 127.0.0.1`; a compose service's `environment` passes each variable whose name marks a credential, by the same rule as the example file, as `${NAME}` without a default rather than writing its value; no Dockerfile declares such a variable with `ARG` or `ENV`, since the image keeps both for whoever pulls it, so a build reads its credential through `RUN --mount=type=secret` and the container receives its own when it starts (a `NEXT_PUBLIC_` name is public by design and exempt); and `.claude/settings.json` denies `Edit(...)` of every generated file and of every pinned managed file, with no local settings allowing one back. `mvn airness:assets-sync` writes those rules beside the project's own.
- **Markdown documents:** every `.md` file a commit would carry is read by the CommonMark parser with GitHub tables and a leading YAML frontmatter block, so a code block, a code span, HTML and frontmatter are never read as prose, and a symbolic link is passed over. Every relative link and image names a committed file, or a directory holding one, in that file's letter case, read against the document's directory or, after a leading `/`, the root; a destination with a scheme or a leading `//` is not followed, a fragment into a Markdown file names one of its GitHub heading anchors or an HTML `id` or `name`, a full or collapsed reference link has a definition, and every definition is used. Every heading is written with `#`, has text, ends in no `.`, `:`, `;` or `,`, descends one level at a time from whatever level the file opens at, and repeats no sibling's title; no section is empty, a comment being no content, and none holds a single subsection. Every code block is fenced, and its opening fence names a language, `text` for plain output. A list nests at most two levels deep and holds at least two items. Each paragraph, the text of a list item and a quoted paragraph included, is one source line: a break inside it renders as a space, so join the lines, and end a line with `\` only where the rendered text breaks, since two trailing spaces count as a cut. No two files hold the same project-owned text, and no paragraph of 80 or more characters, compared as it renders in lower case with its spaces collapsed, appears twice: link to the first place, or replace a copied file with a symbolic link. The managed blocks are left out of that comparison, since Airness writes the same block into every node project, and so is the block between `<!-- BEGIN:nextjs-agent-rules -->` and `<!-- END:nextjs-agent-rules -->`, which `next dev` writes verbatim into the `AGENTS.md` of every Next.js application and adds again once removed; text under markers of any other name is compared. A `SKILL.md` holds at most 4000 words below its frontmatter and the project-owned part of an `AGENTS.md` at most 2000; move a skill's detail into a reference file it links to. Link text names the destination rather than saying `here`, `click here`, `this`, `link`, `read more` or `more`, and every image has alt text.
- **Frontend resources:** at `validate`, every module inventories the scripts (`.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts`, `.tsx`) and stylesheets (`.css`, `.scss`) a commit would carry, whether or not it has a `package.json`. Each must lie in a declared node project and under one of its checked source roots (`src`, `tests`, `scripts` and `airness.sourceRoots`); a script directly in a project's top directory, or in its Storybook configuration directory `.storybook`, is a tooling file the linters and the type check read. `.sass` and `.less` files are refused because no gate reads them. Only a generated file or a file the harness places is passed over; a `vendor` directory or a minified name is not evidence of third-party ownership, so take a distribution from a dependency (a WebJar, or an npm package a `node-run` build copies under `target/`). An ignored input is the concern of `build-inputs` under Repository files and instructions. A tooling project with stylesheets and no script of its own needs no TypeScript, no tests and no server: the script gates report not applicable and the `css` gate judges the stylesheets.
- **Node projects:** every `package.json` in a module belongs to a node project the module lists in `airness.node.projects`, or to a member of a listed pnpm workspace, and every listed directory holds one. A module that lists nothing is checked too. A module that lists a project gets the Node and pnpm the Airness release pins, verified by SHA-256 and cached in the local Maven repository, and each project's locked dependencies, installed with no lifecycle script run. No project may pick a pnpm or Node of its own through `packageManager`, `devEngines`, `useNodeVersion`, `nodeVersion` or `executionEnv`. Build a frontend into the artifact only with an `airness:node-run` execution, the one declaration of the Airness plugin a project may write, with an id of its own and a phase before `prepare-package`. `com.github.eirslett` artifacts, however they reach the build, and `exec` or `antrun` steps that run `node`, `npm`, `npx`, `pnpm`, `yarn`, `bun` or `deno` are refused, because they run a Node other than the one the checks use. Each node project declares `@airness/node` as a development dependency, installed by its version, and in `verify` each of its gates runs in every declared project and in each member of a declared pnpm workspace: `wiring` (the lockfile resolves `@airness/node` at the version of the module's `airness-parent`, never from a local path, with no unapproved override, patch, package extension or pnpmfile hook, and `vitest`, `@vitest/coverage-v8` and `typescript` at the versions the harness runs), `types` (the project's `tsconfig.json` extends `@airness/node/tsconfig.json`, sets no compiler option but `paths`, `baseUrl`, `plugins`, `types`, `rootDir` and `outDir`, keeps the include and exclude the harness names, and type-checks), `biome` (formatting and fast lint under the shipped configuration, with no `biome.json` or `.biome.json` below the project root, passing over Thymeleaf templates, which the Java template checks and the browser sweep judge), `oxlint` (native rules, with no project Oxlint configuration), `eslint` (type-aware lint under the shipped configuration, whatever the project keeps, with no warning allowed and at least one file to lint), `source-rules` (no parent-relative import under a source root, no credential guard that opens when the credential is unset), `config-refs` (every carve-out and declared exclusion reaches a file) and `javascript-allowlist` (no hand-written JavaScript outside the allowlist), `arch` (no cycle, unresolvable import, or production import of a spec, test code or development-only dependency), `type-coverage` (no `any` and no type assertion in hand-written logic, and no `typeCoverage` key), `knip` (no unused file, export or dependency, each judged with every test and tool as an entry point, and also no export, outside the declared public interface, and no file under a production source root that only tests and tooling reach; test such a helper through the production code that uses it, or remove it; a release tag knip honours, `@public`, `@beta`, `@alias` or `@internal`, counts as a suppression), `tests` (the member's own Vitest under the shipped configuration, with 80% per-file coverage), `install-scripts` (`allowBuilds` in `pnpm-workspace.yaml` decides every dependency that runs an install script, and only those; `node-dependencies` installs with every script off and then runs only the approved ones) and `release-age` (`minimumReleaseAge` of at least 1440 with `minimumReleaseAgeStrict: true`, and no resolved release younger than a day by the registry pnpm fetched it from, read on every run, and no git, tarball or directory resolution), and the facets, each not applicable where a member lacks it: `css` (Stylelint and SCSS formatting over authored stylesheets, with no project Stylelint configuration) and `tailwind-tokens` (no arbitrary Tailwind value in a member that declares `tailwindcss`). `tests` also fails a spec outside `tests/**/*.spec.ts` and, in a browser application, `tests/e2e/**/*.e2e.spec.ts`. `release-age` leaves the harness packages, `@airness/node` and the layer packages, out of the age floor, and `minimumReleaseAgeExclude` may name them and nothing else; every other package waits out the floor. Keep that exclusion at a released harness too, since without it pnpm refuses a harness release on the day it is published, and a project moving to that release fails its install. The harness needs no aging because it is the same release as the Maven plugin that runs the build and pins it, so its age adds no supply-chain protection. `npm-inventory` writes the npm dependency evidence in `prepare-package` and judges nothing. In `package`, every npm package it lists that this host installed answers to the license allowlist the Maven artifacts answer to, read as its SPDX identifiers, every package it lists to the npm blocklist, every direct dependency but the harness packages to the freshness bound, read from the registry pnpm installs it from with its configured token, where a release above the one the `latest` distribution tag names is not yet the stable line, and a node project without that evidence fails. The pinned Node answers to the bound in long-term-support lines, and pnpm to the ordinary bound. Extended verification adds `npm-sbom` (a CycloneDX document beside `dependencies.json`), and for a member that declares `next` `build` and `bundle` (gzipped client JavaScript within 1100 KiB), for a browser application `e2e`: the harness's accessibility, layout and security-header specs and the member's own end-to-end specs under the shipped Playwright configuration, and for a member holding a Dockerfile `image`, which builds every Dockerfile of the member, as Node Application Preparation and Security Corrections describes, lists the packages of each image, refuses an image that runs as root, and boots the image of a browser application, hardened, against empty services. A browser application that is not a Next.js application declares the script that serves it as `serve`. A Next.js application gets the React and Next.js lint rules and Biome domains, sends every picture through the image optimizer rather than past it with `unoptimized` or `images.unoptimized`, `arch` keeps `src/app` on top and refuses a routes directory (`app` or `pages`) at the member root rather than under `src`, the pages the crawl renders and `src/proxy.ts` are left to `e2e` rather than to the coverage floor, and the assets goal seeds `src/proxy.ts`. Every `package.json` in a module declares, as a string `license`, one of the license names the repository's root pom declares, and one that declares `LicenseRef-Proprietary` is `"private": true`, which keeps it off every registry. A node project declares only what the harness cannot know, under the `airness` key of its `package.json`, through the keys the table Node Project Settings lists. Diagnose one finding with `pnpm exec airness-node gate <id> --verbose`, which gives no verdict. The sections Node Application Preparation and Security Corrections, Browser Verification and Node Project Settings complete this domain.
- **Maven repository routing:** Airness owns `.mvn/maven.config`, `.mvn/jvm.config` and `.mvn/settings.xml`, since a `-D` option in the JVM options would set a property such as `skipTests` for every build. The startup configuration loads the latter as Maven's global settings and mirrors every remote repository to Maven Central, including repositories introduced by dependency POMs and plugin POM inspection. The local Maven cache and locally installed snapshots remain available. Remote snapshots and artifacts absent from Central are not supported by this policy. Deployment destinations are separate from download mirrors. User settings retain credentials and proxies, but may not add or replace mirrors. The mandatory `repository-policy` preflight checks the three files, the selected global settings and the effective mirror and resolver. Neither `-DskipTests`, report-only mode nor `airness.assets.unmanaged` exempts these files or this check. Run `mvn airness:assets-sync` to adopt an update, then restart Maven. If missing startup settings prevent Maven from starting, run `mvn -gs '${maven.conf}/settings.xml' airness:assets-sync` to restore them, then remove the override. The managed startup files apply before parent and plugin resolution. Preflight detects overrides when the lifecycle reaches `validate`; it cannot undo earlier downloads in an overridden invocation. Initial adoption, explicit repair and standalone third-party goals do not provide an Airness verdict.
- **Dependencies:** explicit scopes, exactly named versions, no project-declared repositories or system paths, released dependencies for a released project, one version and one owning artifact per class, unused dependencies, declared mocking libraries, licenses, known vulnerabilities, available stable package and container-image updates, container tag-digest drift, and the maximum permitted coordinate freshness gap. Some software is refused by name whatever license its own manifest declares, because the license that matters belongs to a server it exists to reach, to a binary it downloads, or to a container image, which has no manifest at all: the MongoDB server and its drivers, starters and embedded forms, Redis images from 7.4, the Elastic images from 7.11 with their clients and APM agent, MinIO, LocalStack, the Bitnami catalogue, CockroachDB from 24.3, the HashiCorp tools under the Business Source License, Redpanda, the Confluent services under the Confluent Community License, Couchbase, Camunda 8, the Timescale images without an `-oss` tag, self-hosted Sentry from 23.11, the proprietary database servers and brokers with the drivers that reach only them, Oracle JDK and Oracle GraalVM whether an image ships them, a workflow or `.sdkmanrc` installs them, or the build runs on them, the Selenium images that ship Chrome or Edge, the commercial Vaadin, Liquibase, Flyway and Hazelcast artifacts, the Develocity extension, iText, Ghostscript, MuPDF, the Gatling Highcharts module, and the AGPL services with a permissive equivalent, among them the Grafana stores, k6, Plausible, Metabase, Garage and Citus. The check reads the raw `pom.xml` of every module including inactive profiles and build extensions, the resolved set, `.mvn/extensions.xml`, every Dockerfile, compose file, workflow and composite action, and every Testcontainers literal in the sources, and a refusal names the replacement. Where a project turned non-open at a known release the refusal starts there, a tag that cannot be placed against that release is refused rather than guessed, and the freshness bound never demands an upgrade into a refused release. Every container image the repository names is pinned to a tag or a digest: `latest` or no tag lets what is pulled change without the repository changing. There is no setting that widens or narrows the list. The reactive stack is refused at `validate`, report-only mode included, where a module's own `pom.xml` declares it, in any profile, under dependency management or on a plugin's classpath, with or without a version, and never where a dependency brings it in: WebFlux with its client and test client, Reactor Netty, R2DBC, the reactive Spring Data starters, RSocket, the reactive Spring Cloud Gateway, RxJava and Mutiny, each refusal naming its servlet or blocking replacement. Reactor itself is not refused, because a project waiting on a library's publisher declares it. Default verification refuses a Dockerfile that upgrades the system packages its base image holds, because a newer release of the base image is the repair, as Compliance Reports describes. It refuses `apk upgrade`, `apk add --upgrade`, `apt-get install --only-upgrade`, and the `upgrade`, `dist-upgrade`, and `full-upgrade` verbs of `apt-get`, `apt`, and `aptitude`. It also refuses the update verbs of `dnf`, `yum`, `microdnf`, `tdnf`, and `zypper`. Compose images remain in scope beside `build` unless a literal service-level `pull_policy: build` establishes local output. External Dockerfile `COPY --from` references are read alongside base images; stage names and numeric stage indexes identify local stages rather than registry images. The known-vulnerability scan reads the effective plugin dependencies Maven resolves from the clean and deploy lifecycles, requested goals, and project build extensions, including plugin dependency overrides. Unused lifecycle defaults enter the scan when requested. A full Airness reactor build collects its own plugin inputs in the parent module.
- **Software bill of materials:** every module generates `target/bom.json` during `package`, using CycloneDX 1.6 JSON and the configured build directory. It lists direct and transitive compile, provided and runtime dependencies, including optional dependencies, and excludes test dependencies. Maven installs and deploys it with the `cyclonedx` classifier. POM modules generate their own inventory too. No timestamp or serial number varies between builds. Generation and its prerequisites remain mandatory with `-DskipTests` and report-only mode. Native skip flags and child replacement configuration cannot disable the SBOM. This is the Maven dependency graph, not a container or distribution-file inventory. Publication checks include the SBOM beside the POM and any required JARs.
- **Repository assurance:** secret scanning, Qodana analysis, the ceiling on how many suppressions the repository holds, complete Git history, commit-message policy, commit typography, linear history, and history-wide compliance.
- **Scripts and infrastructure:** Extended verification runs ShellCheck over supported shell entry points and their sourced repository libraries. The declared shell determines the dialect. Default findings and the compatible optional checks are errors. Checkov reads supported infrastructure and CI inputs through their own framework, so application settings and analyzer configuration are not treated as cloud templates. The fleet policy keeps security requirements and omits requirements for a particular deployment architecture, availability target, retention period, set of log sources, commercial security service, or signing product, and product decisions such as an audience restricted by country. A CLI container needs no health endpoint. A release workflow may declare manual inputs. Extended verification also lints every Dockerfile with hadolint at its default info threshold, loads every compose project with `docker compose config`, and lints every workflow with actionlint. These checks run before Qodana, from staged copies of the committable tree. Each copy is staged in `~/.cache/airness/scan/<tool>-<number>`, beneath the home directory because Docker mounts a folder it does not share as an empty one, and Colima shares only the home directory by default. A scan that passes deletes its copy. A finding or a failure keeps it, with the scanner output beside it, and prints `Scanner evidence: <path>`. `mvn clean` does not remove a kept copy; every scan first removes each copy older than a day, whichever tool and repository kept it, so read the evidence within a day. Missing tools, unreadable inputs, incomplete reports and parsing failures fail verification.

Do not treat a domain omitted from one command's output as ungoverned. The parent POM, bundled configurations, and Airness goals together define the executable contract.

### Managed Files

Each managed path follows one policy. `mvn airness:assets-sync` creates missing files and restores outdated ones, and Default verification fails on a missing or outdated pinned file or managed section, or a missing seed. A layer's files reach the root when any module carries the layer, and a node project's directory once it holds a `package.json`.

| Policy | Paths | Rule |
| --- | --- | --- |
| Managed section | `AGENTS.md`, `.gitignore` and `.dockerignore` at the root, and `AGENTS.md` in each node project directory | the file leads with one block per layer that claims it, between `BEGIN AIRNESS MANAGED: <layer>` and `END AIRNESS MANAGED: <layer>`, in the order `generic`, `java`, `node`; the text below the blocks is the project's, and a stale or unclaimed block fails |

In the Airness repository alone, `.mvn/maven.config` also ends with the two local-repository lines that repository's `AGENTS.md` describes.

### Commit Messages

The section Commit Messages of the governing standard states the policy. A published commit message cannot be rewritten, so an agent satisfies the policy only while writing the message. Airness adds these details:

| Rule | Value |
| --- | --- |
| Header | nothing after the type but the scope |
| Scope | optional, and when present drawn from `a-z`, `0-9`, `.`, and `-` |
| Subject | its length is counted after the `: ` that closes the header prefix |
| Junk words | matched as whole words anywhere in the header, the scope included |
| Body | everything after the first line, stripped, and a blank line after it is the Git convention |
| Typography | plain ASCII only: no em dash, en dash, one-character ellipsis, curly quotation mark, no-break space, or zero-width space |

No commit shape is exempt from the policy, including the headers Git writes by default for a merge and for a revert. Every tool that makes one of those offers to edit the message, so a conforming message is always reachable: a revert says what it undid and why, like any other change. A breaking change is described in the body rather than marked in the header, because a marker a reader has to notice says less than a sentence saying what breaks. No commit message attributes the change to an AI agent or to an AI agent session, and that ban binds in prose as well as by pattern: a marker that no pattern yet knows is still a violation.

Four traps account for most failures:

- The junk-word scan reads the whole header, so `chore(temp): rotate the build cache keys` fails on its scope.
- The 15-character floor rejects a short subject such as `fix typo`.
- The body threshold counts added and deleted lines together, so a routine change crosses it quickly.
- The attribution and typography scans read the body as well as the header, so a signature or an em dash in an explanation fails exactly as it would in a subject.

Check a commit as soon as it is recorded, with `mvn airness:commit-history airness:commit-typography airness:linear-history`. All three goals read the repository rather than the module, so none of them needs a build, and an unpublished commit can still be amended.

### History Shape

The linear-history check counts the parents Git recorded rather than reading the header, so a subject that mentions merging is an ordinary commit, and rewording a merge does not hide it. Avoid a merge rather than plan to repair one: once it is published, only a fresh history satisfies the rule.

### Assertions

The harness checks that every test reaches an assertion and that no assertion compares one written-out value with another. In a node project's Vitest and Playwright specs it also fails a test whose every assertion asks only whether a value exists or is truthy, such as `toBeDefined()`, `toBeTruthy()`, `not.toBeNull()` or `expect(Boolean(value)).toBe(true)`; such checks stay allowed beside one that judges the value. None of these checks decides the question they stand in for, which is whether the assertion would notice if the behaviour went missing. That half binds in prose: a test fails when the behaviour its name states is removed from the code under test. Write each test so that it would, and read it back that way before finishing.

### Node Application Preparation and Security Corrections

A node project may declare `airness.pretest` and `airness.testWrapper` as arrays of literal command arguments in its root `package.json`. The preparation runs before tests, production builds and browser verification. The wrapper receives the pinned Node command and its arguments, so it can provide a disposable database or another isolated environment. Its failure and the actual child command's failure both fail the gate; a wrapper that never completes the requested command fails too. Malformed arrays are refused.

Write the wrapper with `withServices` from `@airness/node/services`, so verifications of several projects, or of two worktrees of one, can run on one machine at once:

```ts
import { randomSecret, withServices } from '@airness/node/services'

const credential: string = randomSecret()
process.exitCode = await withServices({
  project: 'shop',
  containers: [
    {
      key: 'db',
      image: 'postgres:18-alpine',
      environment: { POSTGRES_DB: 'shop', POSTGRES_USER: 'shop', POSTGRES_PASSWORD: credential },
      ports: ['5432/tcp'],
      ready: ['pg_isready', '--host=127.0.0.1', '--username=shop', '--dbname=shop'],
    },
  ],
  environment: (services) => ({
    DATABASE_URL: `postgres://shop:${credential}@127.0.0.1:${String(services.port('db', '5432/tcp'))}/shop`,
  }),
})
```

Each container is named for the run, published on a loopback port Docker chooses and removed afterwards, also when the run is stopped by a signal or killed outright. `network: true` gives the containers a private network, on which `prepare` can run a one-off container with `services.once`; `prepare` also runs steps such as migrations against the services before the command. Never start fixed-name containers on fixed ports, or reuse a developer's database, for verification.

A compose file a developer or an agent starts by hand holds to the same: a host port is a variable without a default, such as `${APP_PORT}`, which the script that starts the project sets to a free loopback port and prints, or it is left to Docker, as in `127.0.0.1::8080`, and no service sets `container_name`. A project whose own URL must be known when it starts, as an origin it accepts requests from, chooses the port in that script.

The Extended `image` gate holds every Dockerfile of a node project to the image a deployment runs. It builds each one with the node project's directory as the build left it as its context, which holds the lockfile and workspace file a member of a pnpm workspace installs by, so a member's Dockerfile names its files from there, as in `COPY web/src web/src`. It passes no build argument and starts no service, so the image cannot depend on a secret or a database at build time, and may copy what `package` made, such as a Spring Boot archive. Every image runs as an unprivileged user: an image whose final stage sets no `USER`, on a base image that sets none either, runs as root and fails, as does one whose `USER` is `root` or `0`, so the final stage ends with a `USER` such as `USER 10001:10001`. For a browser application it then publishes the one TCP port the image exposes on a loopback port of the run, starts the image under the wrapper with `AIRNESS_IMAGE_VERIFICATION=1`, and asks the path of `serverUrl` and each path a stack layer names until every one answers below 500, for at most two minutes; a container that stops, or a path still answering 500 or nothing, fails with the container's log. An answer that names the software behind it, or breaks the caching rules of the security-header baseline below, fails too. The container runs as a hardened deployment runs it: with a read-only root filesystem, no capability and no privilege escalation. Only `/tmp` and the volumes the image declares are writable, so the image declares with `VOLUME` each other path the application writes, such as a cache, and gives the path to its `USER`. In that mode `withServices` runs no `prepare`, so the services start as a fresh deployment's do and the image has to bring an empty database to its schema itself, as its migrations at startup; anything a deployment provisions before the application first starts, such as a bucket, belongs in a container's `ready` command. It also puts the containers on a network of the run's own and hands the command their description, from which the gate passes the image the variables the plan names, each loopback address of a published port rewritten to the service container behind it, and sets each `serverUrlVariables` variable to the origin it serves the image on. A wrapper that does not describe its services fails the gate; a member without a wrapper boots its image with no services. Every container and image the gate starts is removed afterwards, also when the build is stopped. There is no setting that exempts a Dockerfile: one that cannot produce a working image is removed or repaired. Before the gate removes an image, it lists the packages of the image and writes the list beside its result for the compliance report. The listing runs the Trivy image the installed harness pins, which reads a saved copy of the image on its standard input, in a container with no network and no mount. The listing leaves Java archives to the dependency scan, which judges the archives the Maven build puts in an image.

Vitest collects TypeScript and TSX specifications. Server integration specs run in Node, component specs in Happy DOM with native dialog and fetch support, and browser-application unit specs retain their jsdom environment. Application suites and wrapped suites run files serially. The harness network guard loads before an optional project `vitest.setup.ts`, whose imports therefore register matchers and property-test settings against the project's own dependencies. An optional `vitest.global-setup.ts` runs in Vitest's Node host, after the same network guard, and may start real local services for component tests. Use Vitest's provided context to share their addresses and return a teardown that closes them; server code stays out of the jsdom realm.

Only exact security replacements approved by the installed harness are allowed under `overrides` in `pnpm-workspace.yaml`. The generic catalogue belongs to Airness; a trusted stack layer supplies its own `airness.layer.securityOverrides`. Each approval names a parent at an exact version, its dependency, the exact patched version, the advisory identifiers, its reason and date. The workspace declaration and lockfile must agree, every selected dependency edge must resolve to that version, and an unused override fails. Arbitrary replacements, aliases, patches, package extensions and pnpmfile hooks remain forbidden.

A released harness installs its npm packages from the public registry. A SNAPSHOT harness's packages are never published, so the managed `.airness/npm-registry.py` helper can serve their installed Maven tarballs from a temporary loopback registry. Bind its startup and readiness checks at validate, write its endpoint only to an ignored `.npmrc`, and keep its lifetime inside the Maven process. Given the project's lockfile with `--lockfile`, it refuses to start when a served tarball's integrity differs from the one the lockfile records, or when a `package.json` asks for a served version the lockfile records no specifier of, as after a harness version bump, and names the lockfile-only `pnpm install` that refreshes the lock. With `--refresh-with <pnpm>` and the lockfile, bound with the pinned pnpm at validate, before the frozen install at initialize, it serves nothing and runs that refresh itself on a stale lock or one with merge conflict markers, then fails the build, which has rewritten a tracked file, so the next build runs on the refreshed lock. With the `CI` variable set it refreshes nothing and fails. Other packages retain their public registry metadata and release-age checks, and the harness packages stay out of the age floor at a released version as at a SNAPSHOT, as the Node projects domain describes. A Docker build reaches no loopback registry of the host, so an image that installs the development dependencies, as a Next.js build does, builds only against a released harness. While a member declares a harness package at a SNAPSHOT version, the `image` gate therefore leaves out each Dockerfile whose `RUN` installs packages with npm, pnpm, yarn or bun, and judges it once the member depends on a released harness. A Dockerfile that installs nothing, such as one that copies the JAR or the sources it runs, is built and booted all the same.

## Command Workflow

1. Read `airness.package.root` from the root `pom.xml` before adding or moving Java packages.
2. Run `mvn airness:assets-sync` only to create or restore managed repository files, then review and commit its edits. `mvn airness:assets-init` also synchronizes managed files and creates absent optional scaffolds, including a nightly and release Extended verification workflow in a repository with node projects. Scaffolds belong to the project: ordinary `assets-sync` and verification neither require nor recreate them. Customize the workflow's services and environment, or delete it when verification runs elsewhere.
3. Apply formatting, then review the resulting source. In a node project, `pnpm exec airness-node format` applies the same member boundaries, generated-file exclusions and configurations as the Biome, ESLint and stylesheet gates. The Java layer's guide names the format command of a Java module.
4. Run `mvn clean verify` for Default verification. Verify rather than package, because a project that repackages its archive produces the archive that ships during package, and the artifact-content check reads it afterwards.
5. Run `mvn clean verify -Pextended` for Extended verification before finishing, unless a required pull-request gate runs Extended or delta verification on the change. With such a gate, Default verification is enough, and the gate runs the rest. A repository without CI always runs Extended verification locally.
6. To reproduce a failure the gate reported, run the gate's command locally. In a node project, `pnpm exec airness-node gate <id> --verbose` runs one gate, `e2e` or `image` included, and gives no verdict.

Extended verification is the verification command of the governing standard; Default and delta verification run declared subsets of its checks. It includes Default verification and adds the known-vulnerability scan, the HTML/PDF compliance report, and the history, secret, and Qodana checks. Default verification alone never reads the vulnerability database.

A new application begins from a starter, a working application that already passes Extended verification: `mvn eu.ciechanowiec:airness-maven-plugin:<version>:new -Dairness.groupId=<group> -Dairness.artifactId=<artifact>`, run outside any project, writes the `spring-boot` starter into a directory named after the artifact, moves its code to a package derived from both, runs `assets-init`, writes the first `pnpm-lock.yaml` and commits the result as the first commit of a new repository. `-Dairness.package`, `-Dairness.name`, `-Dairness.directory` and `-Dairness.starter` choose otherwise. A SNAPSHOT harness's npm packages are never published, so for one the goal and the application's builds serve them from the local Maven repository, which must hold that harness, with `python3` on the path.

### Browser Verification

Default verification runs no automatic browser sweep; browser tests a project writes itself may run there as ordinary tests. Extended verification runs the complete browser sweep, including Chromium, Firefox and WebKit, alongside the security-header, stack-layer and project specifications. Prepare the Playwright image matching the node harness's pinned `@playwright/test` before the run. A missing image fails with its pull command. The host Chromium used for compliance reports is a separate toolchain.

`mvn clean verify -Pextended,delta` runs the Extended checks with the automatic sweep restricted to affected routes and stories in Chromium. The delta profile requires Extended and cannot be used for a release. Discovery still requests every inventory route, and only the passes are narrowed. It never narrows the project's or a layer's own specifications. Its result and report explicitly state the scope, and its report is a draft rather than a complete Extended verdict. Use Extended verification without `delta` for a release and a full assessment. `pnpm exec airness-node scope --json` explains the selected targets without running verification. The baseline is the remote default branch's merge-base; committed, staged, unstaged and untracked changes all count. Unknown baselines and global inputs broaden the sweep, while unreadable graphs fail. No pass or scope is cached.

The sweep applies to every module that serves user-facing HTML, whatever its backend language. The Java layer's guide states when a Java module is such a web interface, how it is served and where its route inventory comes from; a Next.js application's inventory is the pages under `src/app`, and any other browser application has none, so its discovery follows links alone. After the link crawl, discovery requests every inventory route that names one concrete address and no link reached, and follows its links in turn. A route reached so is discovered like a crawled one, with every pass in every engine, the template sampling and the route ceiling, and the coverage summary lists it as seeded; a seed that does not answer is no broken link. A module with pages behind a sign-in adds `tests/e2e/sign-in.setup.ts`: a Playwright test that signs in, by the project's own means, as the account that reaches the most pages, and then calls `saveSweepSession(page)` from `@airness/node/a11y`. The sweep then visits the application a second time in that session, with the same passes in the same engines. It hands those passes only the pages new to the signed-in visitor: pages only it reaches, and pages whose element structure signing in changed. Each sampling pass still takes one page per template, and the route ceiling counts both visitors' routes together. Signed-in findings and problems say `signed in`. The crawl proves its session on the first route that opens only with it, rechecks that route after every visit and again after the last pass, and fails at the address whose visit ended the session; an address a link or the inventory reaches must not change state. A sign-in that changes nothing the crawl can see also fails. An inventory route neither visitor reaches, such as a pattern with a variable like `/orders/{id}`, which names no address to request, or a page every visitor is forwarded away from, needs a completed `expectSweptPage(page)` scan from `@airness/node/a11y` in a project specification of the current run, which is how other roles, data a specification creates and prepared states are covered, or an `accessibilitySkipRoutes` entry with its reason. The helper records evidence only after every required viewport passes and the URL remains unchanged. Discovery clears earlier evidence before dependent specifications start; teardown checks it after they finish. A source-level call that never executes fails as `route-unexecuted`. Project and layer specifications depend on discovery. Playwright's `--no-deps` is available for a focused diagnostic, which establishes no complete sweep verdict. A temporary redirect (302, 303, 307) credits only the page it lands on, so a protected page answered by the sign-in page stays uncovered for the anonymous visitor; a permanent redirect still credits its source. Same-origin `hx-get` fragments found on swept and scanned pages are requested with the page's session, must answer HTML, and are reported as fragment coverage apart from swept pages.

The node setting `clock` selects an ISO instant or `real`; by default the build, application, test worker and browser start at `2100-01-01T12:00:00.000Z`. Application clocks advance normally; browser Date stays fixed while timers and animation clocks continue. `auxiliaryServers` names the command and URL of each server the application needs before it starts, with an optional member-relative `cwd`. The sweep finds Storybook stories on those servers. In verification, `e2e` keeps the scheme, host and path of `serverUrl` and of each auxiliary URL but serves on a loopback port chosen for the run, handed to the server as `$PORT`, so a `serve` script and every auxiliary command listen on `$PORT`, such as `storybook dev --port $PORT`; the declared port matters only outside verification. An auxiliary command starts without the application's `NODE_ENV`, so it runs in the mode it chooses, as Storybook's development server needs. Specifications reach the application through Playwright's `baseURL` or relative URLs, never a written-out origin. An application that builds absolute links or a list of accepted origins from its own variable names it in `serverUrlVariables`, which the run sets to the served origin, and reads it at runtime. The node harness owns the general browser rules; an installed stack layer supplies the content selectors of its framework's views through `airness.layer.browser`.

The accessibility scan runs axe's default rules and adds, by rule id, the rules axe ships switched off or marks experimental: link purpose (2.4.9), no timed refresh at any delay (2.2.4, 3.2.5), target size (2.5.8), orientation (1.3.4), and the paragraph-as-heading, data-cell-header and faked-caption rules of 1.3.1. A target within a line of text stays exempt, and so does one the visually-hidden pattern clips to a pixel, such as a skip link before it takes focus, because no pointer reaches it. Two links sharing one name that lead to different addresses fail; name each by its destination. Two rules are held to AA unless the project raises them: a pointer target is at least 24 by 24 CSS pixels, or smaller with the room of a 24 pixel circle around it, and `accessibilityTargetSize: "AAA"` raises it to 44 by 44 with no allowance for that room; text stands at 4.5:1, or 3:1 where it is large, and `accessibilityContrast: "AAA"` raises it to 7:1, or 4.5:1. The hover and focus contrast probes measure at the project's contrast level. `scopedAxe` from `@airness/node/a11y` asks the same rule set at the project's levels, read from one file, `configs/axe-options.json` of `@airness/node`; a Java test asks it through `AxeAudit.SCRIPT` from `airness-web-evidence` at AA, or through `AxeAudit.script(targetSize, contrast)` at the levels the project raised.

Resting and reflow measurements keep motion reduced and animations still; only the reduced-motion check below lets reduced motion run unfrozen. Keyboard and disclosure checks also run with normal motion, preserving transitions and animations. They verify that activation opens the disclosure and that focus becomes perceivable, including ancestor opacity, clipping and inert state. Pointer geometry and pixel-contrast comparisons remain in the still passes. Text clipped by a non-scrollable ancestor is a finding; inactive subtrees and text deliberately outside a scrollable region are distinguished from it. An image whose source carries more than three pixels per CSS pixel of its box, decoding at least a mebipixel no screen shows, is `image-oversized`; serve a smaller source, or a `srcset` whose `sizes` match the box. A raster image of at least 100 KiB whose file costs more than four bits per pixel it decodes to, as a photograph saved as PNG or as a JPEG at full quality does, is `image-heavy`; encode it as AVIF, WebP or a JPEG of moderate quality.

Focus and text presentation are held to WCAG 2.2 AAA. No part of a keyboard-focused control may lie under fixed or sticky content (`focus-obscured`). A focus indicator the page draws must change pixels by at least 3:1 over the area of a 2 CSS px thick perimeter of the control, following its border radius, as a 2px solid outline or ring does (`focus-contrast`); a 1px outline, an underline or a tint does not. The browser's own `outline-style: auto` ring, which WCAG exempts, needs only a contrasting line along half the control. No block of text may be justified (`text-justified`), and no rendered line may run past 80 characters, or 40 in Chinese, Japanese or Korean, at any viewport including the desktop one (`line-length`): give prose a measure, such as a `max-width` of about `60ch`. Preformatted text, code and form controls keep their own lines. A block of text set over two lines or more must weigh its last lines together (`text-wrap`): its computed `text-wrap-style` is `pretty`, or `balance` for a heading, so no word is left alone on its last line. The property is inherited, so one `text-wrap: pretty` on `html` or `body` covers a page. Preformatted text, code, form controls and text that never wraps are not judged, nor is a block in an engine that cannot set `pretty`. Each of these is exemptible per element.

A flex or grid group shows its text in document order, the order a screen reader, a braille display and the keyboard follow (`reading-order`, WCAG 1.3.2). It fails when `order`, a `*-reverse` direction, `flex-wrap: wrap-reverse`, explicit grid lines or `grid-auto-flow: dense` shows an item that sets one block of text, such as a term, a figure, a label or a button, before an item that precedes it in the document: a figure shown above its label is announced after it. Write the markup in the order it is shown, such as `<p><strong>12</strong> branches</p>` for a figure and its label. Where the order is intended, as an eyebrow shown above a heading that stays first for heading navigation, exempt the group per element with its reason. An item that sets no text, such as an image moved above a heading, and one holding several blocks, such as a sidebar shown before the main content, are not compared; a vertical writing mode is not judged.

Every class on an element changes what it renders (`class-silenced`). A class fails when another class on the same element sets one of its properties, compared by name, under the same at-rules and pseudo selectors and with the same importance, and wins only because its rule comes later in the stylesheet, while the other classes on the element override every declaration of the class under the condition it declares it: taking the class off the element changes none of its computed style, while taking off the other class does. `text-sm text-lg` fails where the build wrote `.text-sm` after `.text-lg`, since the paragraph renders at the small size and `text-lg` does nothing; a component's default class meets a caller's own that way when Radix `asChild`, a template or string concatenation joins them as plain strings. Remove one of the two classes, or let the component merge its default with the caller's class. Only a utility-shaped class is judged, one every rule of which on the element is that one class followed by pseudo selectors, such as `.text-lg` or `.hover\:text-lg:hover`; a class a component rule also styles there, such as `.card .title`, is not. Classes set under different conditions, such as `hidden md:flex`, a shorthand beside its longhand, such as `p-4 px-2`, an override marked `!important`, a class that keeps a declaration of its own, such as `text-lg` beside `leading-tight` or a block beside its modifier, and a class only a rule under another condition overrides, such as `text-4xl` in `text-4xl leading-tight md:text-5xl` at desktop width, pass. Stylesheet order is the same in every engine, so the resting pass judges it in Chromium at the phone and desktop widths, in the state the page rests in: a pair that applies only under `:hover` is not judged. A stylesheet another origin serves cannot be read, and the finding, or a note when there is none, names it. It is exemptible per element.

The disclosure pass also holds each role to its WAI-ARIA keyboard pattern. A dialog a control opens takes focus, closes on Escape and returns focus to its opener, or to a visible element when the opener went with it; a modal one keeps Tab and Shift+Tab inside (`dialog-keyboard`). Declare every dialog opener with `aria-haspopup="dialog"`, `aria-expanded` or an invoker `command="show-modal"`; an undeclared opener is never activated. A tab list, menu, menu bar, list box, radio group, grid, tree or tree grid, native radio groups included, is one Tab stop, by a roving tabindex or `aria-activedescendant`, and its arrow keys move among its items along its orientation, reversed horizontally in right-to-left text (`composite-keyboard`). At rest and with each disclosure open, `aria-expanded="true"` must leave every `aria-controls` element rendered, a single-select tab list must have one selected tab whose panel alone is rendered (`aria-state`), and a navigation link to the current page carries `aria-current="page"` while no link elsewhere does (`aria-current`). Each of these rules is exemptible per element like the other element rules, on the opener, the widget or the link.

The scrolling pass crosses one route per template and one story per component on an emulated touch phone with normal motion, by wheel gestures down to the end and back. The document must come to rest where each gesture left it (`scroll-hijack`): a page that snaps to sections or runs on past a gesture fails, while sticky pinning and scroll-driven animation, which leave the scroll position alone, pass. A heading, paragraph, quotation or caption not yet seen visible must not stay fully transparent 1.5 seconds after the document rests with it in the upper half of the view (`unrevealed-content`). It reports wheel gestures, not swipes; a project's own specifications cover its touch gestures and any reveal timing tighter than that bound. On the same sample it loads each page again with reduced motion emulated and nothing frozen, scrolls twice and opens the first safe disclosure, and fails content that moves (`reduced-motion`): an animation the step started, of a transform, inset, motion path or margin, lasting at least 100 ms on an element of at least 48 by 48 px, other than on the activated control; a scroll-driven one; an element a script moves on every scroll; and `scroll-behavior: smooth` on a page with in-page links. Fades pass.

The touch pass taps, on the same sample and an emulated touch phone, every button and every element that presents as operable as the interaction pass reads it, other than a link with an address, a summary, a form's submit or reset button, a label whose control the tap reaches and a field. It fails one a tap leaves unanswered - no change to the document, its address or history, a form value, an open popover or dialog or the scroll, and no request, popup or download within 2 seconds - when a mouse click on the same page at the same width, in a context that can hover, answers it (`tap-ignored`). A script asking whether the device can hover or how fine its pointer is hears no on the phone and yes from the mouse, whatever machine runs the browser, so a handler that returns early unless `pointerType` is `mouse`, or unless `(hover: hover)` matches, fails; answer a tap as a click is answered. A control that answers neither a tap nor a click is not judged. It is exemptible per element.

The rendering pass loads the same sample at the phone and desktop viewports with normal motion and nothing frozen, watches each page at rest and across two half-viewport scrolls, and fails an element of at least 48 by 48 px drawn through a `filter`, `backdrop-filter` or `mask-image` whose own animation changes a filter or mask property, inside which an element animates or changes its transform or inset, or which blurs over more than the viewport and itself moves (`filter-in-motion`): each forces the effect to be computed again on every frame. Draw the effect once, as an image or a still gradient, or keep what moves outside the filtered box. It is exemptible per element. The pass also reads Chromium's composited layers at rest and after each scroll, and fails a page whose layers cover more than `layerAreaBudget` viewports, 4 unless the project lowers it, counting of each layer only what lies within one viewport of what is shown and leaving out the document's own layer, its scrolling areas, the viewport and layers that draw nothing (`layer-area`). Drop `will-change` and promoting transforms from what does not move, and keep a layer no larger than what it shows.

After its reduced-motion keyboard walk, the interaction pass fails an element that presents as operable - a pointer cursor it sets itself, an interactive role or an inline `onclick` - when a pointer reaches it, the walk crossed the page without focusing it, and no reached control stands in: an operable ancestor or descendant, an entered composite widget or radio group, a reached link to the same address, or a label's focusable control (`pointer-only`). It dispatches a paste on every password field and every field whose `autocomplete` names a username, password or one-time code, and fails one that cancels it or a password field with `autocomplete="off"` (`paste-blocked`). It then shoots every operable control that shows no text with the control shown and again hidden, and fails one nothing a reader could find of whose drawing contrasts 3:1 with what it covers (`graphic-contrast`, WCAG 1.4.11): the pixels that contrast must cover 9 CSS px², a dot three pixels square, or half of what the control paints when it paints less. An icon drawn in a pale stroke on a pale ground fails, and so does a marker whose only ring is too light against its ground; a dark stroke, a dark icon on a light fill, or a dark outer ring around a light one, passes. A control showing text, an inactive one, and a field - a textarea, a select, or any input other than a checkbox or radio button whose appearance its author turned off - are not judged. It is exemptible per element. Discovery and the resting pass fail a page that moves to another path or opens a window while it loads and settles without input (`unrequested-change`); HTTP redirects and same-path hash, query or history changes pass, and an immediate redirect belongs on the server.

Authored Next.js `not-found` boundaries are scanned through their real application layouts, with concrete locale and dynamic prefixes taken from discovered routes. The expected top-level document 404 is allowed; failed subresources remain findings. A boundary with no resolvable public prefix fails discovery. An application with several root layouts answers an address none of them claims with `global-not-found`, which is scanned at the root; without it Next.js serves its bare built-in page, and that page is judged.

The security-header specification and discovery hold every HTML response to a baseline: `nosniff`, a declared referrer policy, a framing decision and a content security policy that constrains script without `'unsafe-inline'`. The production server a verification run starts also declares Strict-Transport-Security with a `max-age` of at least 31536000 seconds, one year, and marks every cookie it sets `Secure`. A development server owes neither, so send HSTS from production alone: a browser that receives it over HTTPS keeps it for every port of the host, `localhost` included. Every server, a development one included, also names no software: it sends no `X-Powered-By`, which Next.js leaves out under `poweredByHeader: false` in `next.config` and Express after `app.disable('x-powered-by')`, and no product version in `Server`, as in `Jetty(12.0.5)` or `nginx/1.25.3`. Every server also declares the caching of each answer of the application, so that no shared cache, such as a CDN or a proxy, applies a lifetime of its own or hands one visitor's answer to another. Discovery judges the caching of each page's document, of each missing-page probe, of the redirects each navigation followed and of every answer from the application's origin a page loaded, such as a script, a stylesheet, an image or a fetch; an answer from another origin is left to its owner. Each answer carries `Cache-Control`, except an `OPTIONS` preflight, an informational answer and a `302`, `303`, `304` or `307`, which no cache stores on a guess. Next.js declares the caching of its pages and its build's files but sends a route handler's answer as the handler returns it, so a route handler declares its own, or `headers()` in `next.config` declares it for its path. An answer whose `Cache-Control` holds `public` or `s-maxage` without `no-store` fails when it sets a cookie or answers a request that carried `Authorization`, because a shared cache would hand it to every visitor; such an answer is `private` or `no-store`. A cookie the request carried is no sign, because a browser sends its cookies with every file. `expectSecurityHeaders` from `@airness/node/security` applies the same baseline to a response a project's own specification receives, and judges its caching against the request a navigation response names; a request response names none, so a test that sent `Authorization` passes the headers it sent as the second argument.

`expectPerceivable(control)` from `@airness/node/a11y` checks painted visibility within 1.5 seconds, without moving focus or scrolling on the test's behalf. Use it for time-sensitive keyboard regressions.

### Compliance Reports

Extended verification writes one HTML and PDF compliance report for the participating reactor under the root project's configured build directory, in `compliance/`. It embeds one SBOM: every module's Maven artifacts and build tools, every node project's npm packages, every package of each image the `image` gate builds, and the Node and pnpm that ran the node gates, joined in one dependency graph. Every npm package is looked up in the OSV database, and an advisory it lists, or an OSV that can't be reached, fails Extended verification. The common filename is `oss-compliance-report-<root-artifactId>-<12-character-commit>`. Both formats are required, including for plain Java projects. Default verification produces no compliance report.

The compliance report also looks up every package of each image the `image` gate builds. It looks up a system package of an Alpine, Debian, or Ubuntu base image by its source package, and any other package, such as the npm a Node.js image ships, by its package URL. An image built on any other distribution fails the report, and the failure names that distribution. A system package the base image holds fails only once a newer release of the base image ships the fix. The report looks for that release in two places: the release that the base image's tag names when the build runs, and the newest release of the same variant and major version on Docker Hub. The failure names the `FROM` line that takes the release answering the most findings, such as `replace FROM node:26.8.2-alpine@sha256:... with FROM node:26.13.1-alpine@sha256:...`. Until a release ships the fix, the report lists the finding as awaiting a fix, apart from the mitigated ones and never as mitigated, with one of two reasons: the distribution published no fix, or no release of the base image ships the fix it published. The build accepts such a finding until the fix reaches the image. A system package the Dockerfile installs fails once its distribution publishes the fix. Repair it by raising the version its install line pins. When no newer release of the base image fixes a language package of the base image, remove the package from the final stage if the image doesn't use it, as a Node.js application can remove the npm and npx of its base image. Otherwise, record an npm package in `airness.vulnerabilityAllowlist`. Never upgrade packages inside a Dockerfile to answer a finding. The upgrade is refused, and the base image is the repair. A report over a node project whose Dockerfile's image the gate didn't list, as when `airness:compliance-report` runs on its own, is a draft.

Install the Chromium revision this Airness version pins with `mvn airness:report-browser-install`. Linux also needs Chromium's system libraries. The renderer uses this browser's separate cache, not the project's browser-test dependencies or a workstation's interactive Chrome profile. Both installer and renderer explicitly use `~/.cache/airness/report-browser/<Playwright version>`, independently of an inherited `PLAYWRIGHT_BROWSERS_PATH`. Report rendering reads no remote fonts or scripts. Missing browser tooling and incomplete evidence fail generation.

Run `mvn -Pextended airness:compliance-report` to regenerate the prerequisite package-phase evidence and the report outside Extended verification. This command establishes the dependency-policy result, not an Extended verification pass. `-Dairness.compliance.output=<directory>` changes the destination only; it must be ignored by Git or outside the repository and may not traverse a symbolic link.

The first page states the verdict as checked, failed or awaiting statements, without calling the project compliant, beside the key figures; the contents, with every subsection and its page, follow, then a reading guide: where each topic is, every term the report uses in plain words, and what the report does not cover. The report is written for a reader outside the build, names no reader group, and names no build tool as an actor. It then lists every vulnerability the scan read with the affected package's use, worded as the inventory words it, and its status: open, awaiting a fix, or mitigated. Findings of one advisory that share a description and an account are one entry naming every affected package. Every severity is read on one scale, critical, high, medium, low or unrated, and a vector-only rating is computed from its CVSS 3 base vector. The report prints the account of each finding that awaits a fix and a mitigation plan for each mitigated one from its suppression entry. It follows with the license classes, every weak copyleft or refused package with its uses, the inherited license policy with every declared license spelling it read as another identifier, and the full inventory, grouped as Maven artifacts, npm packages, build tools and container image packages: every resolved package, the license identifier the policy reads it as, and its use. A use is production, provided, test, build or development, direct or transitive. An npm package is a production one when a workspace member reaches it through its `dependencies` or `optionalDependencies` in the lockfile, and a development one otherwise. The system packages of each image the `image` gate builds are listed with the licenses their distribution declares, and the license policy doesn't judge them. The report ends with the license and notice files that each production package carries, a Maven artifact's from its archive and an npm package's from its installed directory. Identical texts are grouped with their package attribution.

The HTML embeds an aggregate CycloneDX inventory and a CSV inventory for download. The CSV keeps each declared license beside the identifier the policy reads it as. Published per-module `bom.json` files retain their existing production dependency scope. The report records its source commit, working-tree fingerprint, evidence hashes and scan dates. It refuses missing or stale evidence and a tree that changes during generation. A dirty tree, selected reactor subset, policy failure or report-only invocation produces an explicit draft. `-DskipTests` produces no new report or verdict. Earlier report pairs are removed only after a complete replacement has been rendered.

## Exceptions and Repairs

- Fix a managed-file finding with `mvn airness:assets-sync`. A seed's contents belong to the project after creation, but its path remains mandatory. A project may take over an eligible path through `airness.assets.unmanaged` only when the assignment explicitly requires it and the project records the reason.
- Fix formatter findings with the format command of step 3 of the Command Workflow. Modernization findings name the form to write, and no command writes it for you. Fix compilation, analysis, dependency, test, coverage, history, security, and tool failures at their source; do not disable the failing check.
- Change an exclusion or the default test timeout only for an explicit project requirement. Never use one merely to obtain a pass.
- The test order seed and the suppression ceilings are the harness's own and take no project setting. The Java sources of the build hold three suppressions per thousand lines, and never fewer than five, and each class pattern of `airness.coverage.excluded.classes` counts as one. The node projects' own code holds two, and one more per 500 non-blank lines, with each `coverageExclude` entry counting as one. Answer a suppression-ceiling finding by removing a suppression, and never by trying to raise the ceiling.
- So is the Git configuration a test reads. Every Surefire, Failsafe and Vitest run reads the managed `.airness/test.gitconfig` as its global Git configuration and no system one, through `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM`, which a project file may not set. It turns hooks, commit and tag signing and the machine's ignore and attribute files off, starts a repository on `main` and commits under a fixture identity, so a developer's or a CI image's Git configuration never decides a verdict. A test that needs another Git setting writes it into its own fixture repository.
- There is no setting that turns a check off. If a check is wrong for the project, that is an Airness bug to be fixed in Airness, not a local override.
- ShellCheck, Checkov, hadolint, actionlint, and Trivy accept no project-owned suppression or replacement configuration. Their image pins and policy are carried in the installed Airness artifacts, so even a command-line image override cannot replace them. A ShellCheck source hint must identify the actual repository import, never an empty substitute. The scanners read only regular committed files and never follow a symbolic link: a link to a committed file, or a directory holding one, inside the repository is passed over, since its destination is scanned as itself, and a link that dangles, leaves the repository or leads to something nothing commits fails the scan. Report a false finding to Airness.
- A configuration file a pinned tool would read from the tree on its own is refused on every build, tracked or not: the scanners' native files, `.gitleaksignore`, which gitleaks reads whatever its flags say, and the `junit.jupiter.execution.timeout.*` keys of a `junit-platform.properties`, which the parents pin as launcher parameters. A fixture exception belongs in `.gitleaks.toml`, and the rest of `junit-platform.properties` stays the project's. That exception names its `targetRules` and writes the whole fixture as `'''^value$'''`, a literal string matched against the secret, because gitleaks excuses every finding that contains an unanchored value and decodes the escapes of a double-quoted one before compiling it.

### Vulnerability Exceptions

Reach for the OWASP suppression file, which `airness.dependency-check.suppression.file` locates, only when no upgrade answers an advisory. Every entry of that setting names an existing file inside the repository: a URL, a `file:` URI, a missing path or a path outside the repository is refused. Keep it at `.airness/dependency-check-suppressions.xml` in the directory of the module whose dependency it excuses, which is the path the scan of that module reads: the document's presence there is what puts it in front of the scan, so one kept elsewhere is never read and the setting itself needs no declaring. In a multi-module build a document at the repository root excuses nothing in a child module. Every rule in it names the advisory it excuses and carries `notes` with three parts. The notes say why the vulnerability can't be exploited in this project: name the path that reaches the artifact, whether it runs in production or only in tests and the build, and why its input can't trigger the defect. After a `Mitigation:` marker they state the mitigation plan: what limits the risk now and what will remove the artifact, such as the upstream release or the dependent's upgrade it waits for. They carry a `YYYY-MM-DD` date. A rule that suppresses nothing fails the build, like every other exclusion that reaches nothing. The harness carries its own narrowly scoped, dated exceptions for confirmed incorrect product or version matches, and the project's rules add to them.

```xml
<suppress>
    <notes><![CDATA[
        Added 2026-01-15. example-parser is reached only through example-bundler, which parses the project's own
        build configuration during the build. The defect needs attacker-supplied input, which that configuration isn't.

        Mitigation: example-bundler never runs in the deployed application. The entry is removed once
        example-bundler releases a version that drops example-parser.
    ]]></notes>
    <packageUrl regex="true">^pkg:maven/org\.example/example-parser@.*$</packageUrl>
    <cve>CVE-2026-0001</cve>
</suppress>
```

The compliance report prints the reason and the mitigation plan to a reviewer outside the project, so write both as complete sentences that stand on their own.

Each exception names non-empty literal `cve` or `vulnerabilityName` values. Advisory-name regexes, product (`cpe`) and weakness (`cwe`) selectors, and CVSS score thresholds are refused, even beside a named advisory. Dependency selectors (`packageUrl`, `gav`, `filePath` and `sha1`) remain available, including their supported regex forms, and a dependency selector is not mandatory. Entries in groups and entries using namespace prefixes are checked too. Each entry carries its own explanation, mitigation plan and date.

A system package of an image needs no exception, because the harness records each finding that no release can fix yet, as Compliance Reports describes. Each `airness.vulnerabilityAllowlist` entry carries `package`, `advisory`, `reason`, `mitigation` and `addedOn`. Name one exact npm package and one literal advisory identifier or an alias OSV supplies, explain why it cannot be exploited here, state the removal plan, and use a YYYY-MM-DD calendar date. Prefer an available, compatible upgrade or an approved security replacement. An exception belongs only to that node project's inventory: it cannot excuse another module or frontend. Missing fields, malformed declarations, unused entries and overlapping entries fail verification. The report keeps each mitigated advisory and its explanation, while any remaining open finding still fails. A scanner that cannot run cannot be waived.

### Change Requests

A project cannot repair the harness from inside itself, and that is the design rather than a gap in it: a rule a project can edit is not a rule. What follows from it is that a rule improves only when somebody reports it, which makes the report part of the contract rather than a courtesy.

Raise it with the Airness maintainers when:

- a check blocks work that is correct, and the only way past it is a suppression or an exclusion;
- the same finding is repaired the same way in project after project, which is a rule that belongs in the harness rather than in each project's habits;
- a project-owned check turns out to be true of every project of this kind, and should move into the harness;
- a message names a defect without naming the repair, or names the wrong repair.

Bring the failing output, the smallest case that reproduces it, and what the rule should have said. A suppression to get past a check is a local answer to a general problem: take it when the work cannot wait, and report it either way, because the next project meets the same check with no memory of this one, and a suppression left in place spends a ceiling the next repair will need.

## Settings

### Project Settings

| Setting | Use |
| --- | --- |
| `airness.package.root` | the prefix of every production and test package, and the only required key |
| `airness.assets.unmanaged` | repository paths the project takes over from the harness |
| `airness.node.projects` | the module's node project directories, comma-separated, and none unless set |
| `airness.generated.files` | further generated files, comma-separated |
| `airness.typography.excludes` | repository path prefixes the typography scan skips, never all of them; generated files are skipped without it |
| `airness.coverage.excluded.classes` | `pattern -- reason` entries, separated by semicolons, for the classes the coverage floors skip, never all of them; each counts against the suppression ceiling |
| `airness.test.timeout` | the ceiling on one test, and `30 s` unless set |
| `airness.dependency-check.suppression.file` | a local OWASP suppression file, and the path Vulnerability Exceptions names unless set |

Those eight are the whole of what a project file may declare. Every other name under `airness.` is refused there, and so is every property a goal the parents bind reads in place of a parameter that decides a verdict, such as `skipTests`, `maven.test.failure.ignore`, `checkstyle.maxAllowedViolations` or `license.excludedGroups`, because Maven fills an unset parameter from that property without the plugin being declared. A property that only tunes how a plugin the project may configure runs, such as `argLine`, stays the project's. The refusal reads the file as written, so a name inside a profile that is never activated is refused too. So is a profile whose id an Airness parent owns, `delta`, `extended`, `format`, `release` or any `airness-` id, because Maven activates a profile of that id beside the harness's own; only the invocation's `-Pformat` selects formatting. Both `-Dairness.enforce=false` and `-DskipTests` are command-line flags and are never written into a project file. Raw-model integrity checks read the current POM and every consumer parent up to the trusted Airness chain, even with `-DskipTests`; skipping execution cannot hide a forbidden committed property or inherited override.

A property naming a version is refused where nothing in the same file reads it. The platform reaches a project as a bill of materials the parent imports rather than inherits, and an imported one resolves its own properties, so a `tomcat.version` written beside the settings above moves no version at all and leaves the file claiming a pin that is not there. Manage the artifact in a `dependencyManagement` block of the project's own and version it from the property, which is what makes the property the pin it reads as.

### Node Project Settings

A node project declares what the harness cannot know through these keys under `airness` in its `package.json`:

| Setting | Use |
| --- | --- |
| `sourceRoots` | first-party source directories beyond `src`, `tests` and `scripts` |
| `generatedArtefacts` | files a generator writes, which no gate judges |
| `frameworkGlue` | files a framework writes to a fixed shape, which the lint relaxes |
| `javascriptAllowlist` | JavaScript files a tool forces on the project, each with the `runtime` of `node` or `cloudfront-js-2.0` that runs it |
| `coverageExclude` | source files the coverage floor doesn't measure; each entry counts against the node suppression ceiling |
| `pureLogicRoots` | directories of pure logic, which `arch` forbids to import anything else under a source root |
| `productionEntries` | files that run in production though no entry point knip reads reaches them, such as a script `start` runs or a site build that renders a story; never a test, and no suppression |
| `accessibilityTargetSize`, `accessibilityContrast` | `"AAA"` raises the size of a pointer target to 44 CSS pixels and the contrast of text to 7:1; `"AA"`, the default, keeps 24 pixels or the room around a smaller target, and 4.5:1 |
| `accessibilitySkipRoutes` | route prefixes the sweep doesn't follow |
| `serve`, `serverUrl`, `serverUrlVariables`, `auxiliaryServers`, `clock` | how a browser application is served and the clock it starts at, as Browser Verification describes |
| `bundleBudgetBytes`, `accessibilityRouteBudget` | lower ceilings for the client bundle and for the routes the sweep discovers |
| `layerAreaBudget` | a lower ceiling, in viewports, for the composited layers the rendering pass counts |
| `layoutMinimumGap`, `layoutViewports` | a larger gap between boxes, and further viewports the layout scan measures |
| `pretest`, `testWrapper` | the preparation and the wrapper that Node Application Preparation and Security Corrections describes |
| `vulnerabilityAllowlist` | npm advisories that can't be exploited here, in the root node project only |

Each `generatedArtefacts`, `frameworkGlue`, `javascriptAllowlist`, `coverageExclude`, `pureLogicRoots`, `productionEntries` and `accessibilitySkipRoutes` entry names a `pattern` and a `reason`.
